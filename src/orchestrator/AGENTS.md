# Orchestrator DOX

## Purpose

The `src/orchestrator/` subtree centralizes LLM run execution, tool calls, streaming events, abort handling, and skill-instruction injection.

## Ownership

- `RunOrchestrator.js` owns run IDs, active run state, tool execution idempotency, registered built-in tools (including the reserved `web_search` tool), provider-specific execution, and follow-up calls after tool execution.
- `PageTaskMemory.js` owns bounded long-run notes and page-snapshot history compaction; notes are untrusted observations held only in the live run, and note validation rejects secret, credential, and payment wording.
- `ActPlanner.js` owns session-scoped sub-goal decomposition for long-horizon Act runs. Active planner state lives in `run.pageActions.planner`; a separate bounded session checkpoint stores only metadata before a mutation for explicit Resume after a worker restart. The checkpoint never stores DOM, page text, notes, credentials, or raw values. The planner activates automatically when the user instruction exceeds 100 characters or contains multi-step signals (then, after, next, numbered lists, etc.). It emits one user-facing `page_action_notice` after the first message is ingested. It caps sub-goals at 8 per run (each ≤200 chars) and replans at 3 per run to prevent infinite decomposition loops.
- `CodexTransport.js` owns the ChatGPT subscription Responses request/input/tool conversion and SSE parsing. `RunOrchestrator.js` remains the owner of Codex tool execution, policy, skills, recovery, and Prompt Paul event shapes.
- `HermesTransport.js` owns authenticated or explicitly trusted-network Hermes gateway requests, session creation and stale-session recovery, bounded SSE parsing, pollable run-status recovery, and server approval calls. Hermes server tools remain gateway-owned; Prompt Paul only adapts safe lifecycle events and renders approvals.
- `runResilience.js` supplies the shared long-run controls used by provider transports and `RunOrchestrator`: bounded retry classification, reasoning-aware request timeouts, deterministic context compaction, and repetitive-output detection.
- Provider transports use `src/utils/streamSafety.js` for bounded SSE buffers and error-body reads.
- The orchestrator exposes `run.webSearch` metadata only through the terminal `complete` event (`event.grounding.sources`); the Brave API key never leaves the service worker.
- Current-page actions are opt-in per run through `config.pageActions`, source-tab scoped, and registered as the reserved `page_get_state`, `page_find_text`, `page_click`, `page_input`, `page_select`, and `page_scroll` tools. Their executor is injected by the service worker; the model never receives browser APIs or selectors. Valid HTTP(S) links may navigate under the bounded Act lease; writes and risky controls remain confirmation-gated. An unexpected transition in the active target tab is recoverable after the service worker observes the new URL and re-establishes the content-script bridge, then the orchestrator discards stale state and forces `page_get_state`. Page-action state events may notify the current target tab so the browser-page notch can show a temporary branded activity glow.
- The Act lease includes owned-tab list/open/switch/close tools, limits a run to twelve tabs, blocks closing the source tab, and does not require a second Tabs permission. `page_open_tab` keeps one work tab per site: a requested destination already shown by an owned tab (matched on origin + path, ignoring query/fragment) is adopted in place — `reused: true` with the normal ready/tabError contract — and any other same-origin open navigates the run's existing non-source tab to the new URL (`navigated: true`, source tab never hijacked, unavailable tabs skipped) instead of creating a duplicate tab; `page_open_link` navigates the current target tab in place by default; `background: true` delegates to the owned-tab opener for explicit multi-page research. The Act prompt states that ordinary work stays in the current tab, directs the model to call `page_list_tabs` before opening a separate tab, reuse the site's work tab, and never re-perform a step whose receipt, note history, or planner state already shows success. Opened and switched tabs pass a bounded document/bridge readiness check; background tabs do not retarget the run. A bridge failure quarantines only the affected tab and allows the run to continue on another healthy tab; after a user reload, a fresh `page_get_state` can re-probe the failed source tab. Run teardown clears the page-action session in every owned tab before disposing the lease.
- `page_request_user_input` is a bounded clarification tool. It is available only in an Act-enabled run, blocks secret/payment questions, and waits for an extension-page response with a timeout or abort path. `page_pause_for_user` is a separate safe manual-intervention checkpoint that requires explicit Resume and fresh inspection.
- Act owns the first tool turn: when `config.pageActions` is enabled, `page_get_state` is the only advertised and forced tool until the initial snapshot exists. A forced custom tool choice resumes only after inspection. The Act prompt must name the authoritative callable page tools and tell the model not to claim that those tools are unavailable.
- The page-actions system-prompt block is directive and non-limiting: the model must execute page-achievable requests with the page tools (inspect → act → re-inspect → summarize what it did) rather than describing steps. The block deliberately never enumerates capabilities the tools lack (terminal/OS actions, JavaScript, unsupported navigation), because that enumeration drove models to lead with “I can’t” refusals; `page_find_text` provides bounded read-only search for exact filters, labels, prices, and interstitial messages before scrolling; requests the tools cannot execute are answered normally as a helpful assistant, and the model never fakes an action. Approved navigation-capable controls may transition the current tab once; unexpected active-tab changes discard the old snapshot and require `page_get_state` before continuing the same request. The model must follow that recovery notice instead of claiming that page tools are unavailable. Validated HTTP(S) links may navigate under the bounded Act lease; `page_open_link` navigates the current target by default, while `background: true` opens a separate owned tab for explicit multi-page work. Safe new origins do not require a second permission prompt. Secrets stay out of the page tools. Empty snapshots tell the model to ask the user to open the target page.
- Page-action policy is snapshotted at run start. Default mode confirms state-changing actions; trusted mode only skips allowed low/medium-risk approvals. An approval-card “Approve all this session” choice is scoped to the active run and skips every confirmation for policy-allowed actions; credential, OTP, payment, security, destructive, navigation-link, and unsupported actions that are hard-blocked remain unavailable. Planner-activated runs request one initial state-changing-action approval, then auto-approve only low-risk non-navigation actions for that run; high-risk and navigation actions remain confirmation-gated, and denial leaves planner auto-approval disabled (hard-block fail-safe).
- Act-mode instructions require the model to continue multi-item or ongoing page workflows after partial progress instead of returning an interim next-step menu; it may ask only when real ambiguity, a blocked action, or a safe manual step prevents progress.
- Brave execution is supplied through `braveSearchExecutor` and key availability through `webSearchStatusProvider`; `run.config.apiKey` is only the selected LLM credential.
- Search/tool sequencing is model-directed before use: a forced user tool (when configured) runs first exactly once, then `web_search` is offered with automatic model selection (never forced) while a search slot is available. The slot is claimed before network I/O.
- After a search attempt, the system prompt switches to an already-completed phase and the immediate continuation is text-only. Duplicate or parallel search calls receive `WEB_SEARCH_ALREADY_USED` and never issue another Brave request.
- A search response with no usable normalized sources produces `WEB_SEARCH_NO_RESULTS`; it is not treated as successful grounding.

## Local Contracts

- Navigation links are supported only when the snapshot exposes a validated HTTP(S) destination. Same-tab links use `page_click`; links that open a new tab use the indexed `page_open_link` tool. Safe cross-origin navigation is covered by the Act lease, while writes and risky controls still require approval. An active target tab that changes documents independently is adopted automatically and inspected before any mutation.

- Skills are injected as instructions via the composed system prompt (`_buildSystemPrompt`), not via conversation history unshift. Requested skills are resolved through `resolveSkill` and included even when `disable-model-invocation` hides them from model self-discovery.
- Tool executions must remain idempotent by `runId` and `toolCallId`. Before every state-changing page or owned-tab action, the orchestrator persists a bounded session checkpoint. Failed or interrupted dispatch leaves an in-flight checkpoint for explicit recovery; normal completion and terminal cleanup remove it. Mutation uncertainty is never resolved by blind replay.
- The tool-call retry cap counts consecutive failing tool turns only: a successful tool result resets the counter, so multi-step page automation (inspect → act → re-inspect) can run up to separate observation/navigation/mutation budgets (192/72/48). Bridge readiness and navigation polling use bounded exponential backoff with jitter. Mutation results carry a refreshed-snapshot notice and a bounded selector-free `scopeDiff`, so the model re-reads the current `snapshotId` and indexes instead of reusing stale ones. State-changing page actions return bounded delivery receipts with action-specific evidence; unchanged `delivered_unverified` mutations are not retried. The same-mutation loop guard records only executor-delivered mutations, so stale or obscured dispatch failures cannot lock out the required action; three delivered repeats without visible change still block. `page_record_note` stores up to 48 short untrusted observations for long tasks, rejects secret/credential/payment wording, and old page snapshots are compacted before provider calls (history cap 240K chars).
- The sub-goal planner evaluates progress after each `page_record_note` call using one fresh action receipt and note text; verified mutation and goal-relevant read-only receipts can advance the current sub-goal, and the receipt is consumed so duplicate notes cannot advance multiple goals. Every planner receipt is bound to the sub-goal index active when the action ran, so a receipt cannot advance a different goal. Required post-mutation inspections do not overwrite a pending mutation receipt, and successful owned-tab actions receive bounded verified receipts. Mismatched action evidence does not advance a goal. Repeated failures (≥2 attempts) block and skip it. `page_replan` replaces unresolved goals up to three times and groups overflow work into a visible remaining-work goal. The planner prompt block is injected into the system prompt each turn showing current sub-goal, progress, upcoming goals, and remaining budget. If the model returns text while goals or final verification remain unresolved, the orchestrator issues bounded continuation turns instead of silently completing. When all sub-goals resolve, one fresh `page_get_state` verification is required before page tools are removed and the effective tool choice becomes text-only so the model produces a final summary.
- Abort handling should emit a clean aborted event rather than surfacing intentional cancellation as an error.
- Provider-specific execution must preserve OpenAI-compatible and Anthropic-compatible endpoint behavior. Non-Hermes provider loops count API calls separately from tool calls, allow one toolless wrap-up call after a 500-call or 30-minute default limit, retry only bounded transient failures, compact oversized histories, and never repeat a delivered provider response after an output-safety failure.
- Hermes provider execution must use the stored Hermes profile endpoint, never accept a credential from a chat message, and may use Act/page actions only after the gateway advertises `run_client_tools` plus the documented `/v1/runs/{run_id}/tool-result` route. Client calls must pass through the existing bounded page-action policy, approvals, ownership, and receipts; unsupported gateways reject Hermes Act runs. Hermes runs send the trailing unsent local user messages as current-turn input plus a bounded explicit `conversation_history`; loaded page context stays attached while it is active and historical binary media is removed. Hermes session pointers are bound to the local conversation identity. Hermes session boundaries use `PATCH /api/sessions/{id}` with a fixed `new_conversation` end reason; only the documented `session_not_found` response may clear an already-missing pointer. Stale-run recovery must not treat unrelated 404 responses as missing sessions. One Hermes run or stopping run is admitted per profile; different profiles may run independently. Hermes Stop keeps the active run and profile guard until a remote terminal state, and control-plane requests use bounded timeouts. Hermes capability checks require the advertised run submission, status, SSE, stop, and approval features before the connection is reported as supported; released gateways (0.20.x) advertise the approval feature as `run_approval_response`, which the check accepts alongside the documented `run_approval` name. Hermes approval decisions must match the pending opaque approval ID.
- Codex subscription runs use the background-provided access token and account identifier only at request time; never persist or emit those values through run state, journals, or UI events. The selected profile reasoning level is sent as the Codex Responses `reasoning.effort` field.
- Terminal `complete` events may include safe provider completion metadata. Reasoning-only responses receive at most one text-only recovery attempt without repeating tools or exposing hidden reasoning.
- `CORE_INSTRUCTIONS` applies to all runs unless the project deliberately changes the formatting policy.

## Work Guidance

- Keep orchestration logic centralized here instead of duplicating run or tool execution flow in `background.js`.
- Hermes server tools remain gateway-owned; do not register Prompt Paul custom-tool handlers for Hermes runs.
- Register new built-in tools through the existing tool registry pattern.
- Keep skill policy aligned with root AGENTS.md and `src/utils/skillParser.js`.
- Preserve event shapes consumed by `chat.js`; page-action confirmation events must include only bounded summaries, risk, target labels, and opaque confirmation IDs, never raw DOM values or secrets.
- Runtime events carry a monotonic per-run sequence and a bounded session journal. The journal stores safe activity summaries only; raw DOM snapshots, tool arguments, credentials, and streaming deltas are not persisted. Development diagnostics use a separate bounded session store and must redact credential-shaped data; detailed response payloads can be console-only when they would exceed the normal journal contract.
- The background `executeRun` message is an acknowledgement boundary, not a completion stream. The worker starts `RunOrchestrator.execute()` without holding the sender's message channel open; terminal events and the bounded journal are authoritative for completion or failure.
- Development tracing is separate from the normal event stream. `RunOrchestrator` records detailed local run, provider, tool, page-action, policy, receipt, budget, planner, and recovery diagnostics only when the development build's session tracer is enabled; production builds replace the tracer with a no-op.
