# Orchestrator DOX

## Purpose

The `src/orchestrator/` subtree centralizes LLM run execution, tool calls, streaming events, abort handling, and skill-instruction injection.

## Ownership

- `RunOrchestrator.js` owns run IDs, active run state, shared tool execution idempotency, registered built-in tools (including the reserved `web_search` tool), common provider callbacks, and follow-up calls. `OpenAIExecution.js` and `AnthropicExecution.js` own their provider request/stream loops and install those methods onto the orchestrator host; `src/act/ActExecution.js` installs the Act execution methods that operate on the same host-owned run state.
- Explicit `answerFormat: 'cards'` runs use the shared answer-schema decoder for text events and normalize the final readable answer before assistant history and terminal journaling. Bounded `answer_cards` events may carry complete validated prefixes and host-issued provider-turn identity; the live completion decides whether cards remain. The journal retains bounded readable text and excludes card projections/local state. Card parsing never starts repair requests or tool execution.
- Act execution, planning, outcomes, working memory, scroll identities, action limits, tool schemas, and task notes are owned by [`src/act/`](../act/AGENTS.md); import its public API through `src/act/index.js`.
- Page-state observations include supported ARIA widget controls and bounded state flags; SPA query/fragment changes are reported only as an 8-character route digest and a boolean. Route-change receipts contain only the `route_changed` evidence kind, never raw query/fragment data.
- Every `page_get_state` action reads the current page through the content-script bridge; do not cache snapshots across inspections because page state can change without a document navigation.
- Scroll delivery is verified from the returned merged snapshot only when the window or a visible scroll-container position changes. An executor receipt alone cannot claim progress. Exact no-movement retries are blocked, and at most three distinct scroll attempts may be dispatched from the same unchanged snapshot state. When a moving scroll revisits a previously observed position on the same document and route, `page_scroll` is removed from the next provider tool list and direct repeated calls are blocked; a matching text result or verified navigation/mutation restores it. Continued movement through new positions remains available. These limits are run-local.
- Malformed tool arguments may recover a valid JSON suffix only when the discarded prefix contains no JSON structural characters. Never salvage an inner object from a malformed outer call; doing so can silently drop required fields and change the intended action.
- A delivered-unverified mutation may return a fresh same-document snapshot that grounds the next action without another inspection call; this is observed state, not proof the requested effect succeeded. When no current snapshot is returned or the document changes, offer only `page_get_state` until recovery. Final task verification still requires a separate fresh `page_get_state`.
- Non-Hermes Act runs execute their initial inspection before the first provider request and add a matching synthetic assistant tool call/tool result pair. Initial tool selection is automatic; recovery without a snapshot still exposes inspection only. Hermes retains gateway-directed first inspection. Page tool results use `pageActionResult.js` for model serialization while full snapshots remain internal.
- Indexed hover resolves the target key under the same stale-state checks as mutations but consumes observation budget. Owned-tab back navigation consumes navigation budget, checks readiness and discards the old snapshot before further actions.
- Keyboard actions bind an indexed or freshly observed focused element to a snapshot and internal element key. Enter/input submission use the form submit control policy. Focus or submit-control identity changes require reinspection before delivery.
- `CodexTransport.js` owns the ChatGPT subscription Responses request/input/tool conversion and SSE parsing. `RunOrchestrator.js` remains the owner of Codex tool execution, policy, skills, recovery, and Prompt Paul event shapes.
- `HermesTransport.js` owns authenticated or explicitly trusted-network Hermes gateway requests, session creation and stale-session recovery, bounded SSE parsing, pollable run-status recovery, and server approval calls. Hermes server tools remain gateway-owned; Prompt Paul only adapts safe lifecycle events and renders approvals.
- `OpenAIExecution.js` and `AnthropicExecution.js` own the API provider request and stream-processing loops. Their methods are installed on the orchestrator host to share run lifecycle and tool state; common policy, tool execution, and event lifecycle stay in `RunOrchestrator.js`.
- `runResilience.js` supplies the shared long-run controls used by provider transports and `RunOrchestrator`: bounded retry classification, reasoning-aware request timeouts, deterministic context compaction, and repetitive-output detection.
- Provider transports use `src/utils/streamSafety.js` for bounded SSE buffers and error-body reads.
- The orchestrator exposes bounded `run.webSearch` source metadata through live card events and the terminal `complete` event (`event.grounding.sources`); the Brave API key never leaves the service worker.
- Current-page actions are opt-in per run through `config.pageActions`, source-tab scoped, and registered as the reserved `page_get_state`, `page_find_text`, `page_wait`, `page_batch`, `page_click`, `page_input`, `page_select`, and `page_scroll` tools. Every tool advertises an optional bounded model-supplied `title` (≤80 chars) displayed on the progress card and validated/sanitized by `pageActionPolicy.js`; the title never reaches the page or the journal raw. Their executor is injected by the service worker; the model never receives browser APIs or selectors. The `page_batch` provider schema uses flat per-action fields to avoid malformed nested arguments; its boundary normalizer still accepts both flat and nested internal representations. Prefer individual calls when one observation must guide the next action. `page_find_text` stays read-only; its result indices and snapshot ID must resolve against the orchestrator's current merged snapshot, and it may return bounded, sanitized URLs plus matching context for exact text found in semantic result cards, including offscreen cards, so the model can open an observed match without guessing an index. Observed HTTP(S) links may navigate under the bounded Act lease; unrequested model-entered cross-origin URLs require confirmation, while writes and risky controls remain confirmation-gated. An unexpected transition in the active target tab is recoverable after the service worker observes the new URL and re-establishes the content-script bridge, then the orchestrator discards stale state and forces `page_get_state`. Page-action state events may notify the current target tab so the browser-page notch can show a temporary branded activity glow.
- A page action with a stale snapshot is never dispatched. The orchestrator immediately requests a fresh `page_get_state` and includes its snapshot in the `PAGE_STATE_STALE` tool result when inspection succeeds, so recovery does not need an extra model call; pre-dispatch stale failures refund their budget and carry a `not_delivered` `stale_snapshot` receipt. The model must use the returned snapshot's IDs and indices. `page_find_text` indices are translated from the top-frame local snapshot into the current merged positional indices; unmapped or stale local indices are dropped.
- A repeated scroll in the same direction from an unchanged page/scroll position is not dispatched again after its prior receipt was unverified; return the current snapshot and direct the model to a different observed container, exact-text search, or observed link. Bound this run-local history and clear it after verified scrolling.
- `CdpInputBackend.js` owns the default-off precise-input debugger session. Commands time out after 15 seconds; a timeout is never retried because input may already have been delivered. A state-changing action that times out without navigation pauses for user intervention because a JavaScript dialog or busy page may block the bridge. It may call only `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, and `Input.insertText` with bounded parameters; it must never expose DOM, Runtime, Page, Network, screenshot, or arbitrary CDP methods. Stop, run teardown, and errors detach the debugger. If a command may have been delivered, do not retry the same mutation through DOM events.
- The Act lease includes owned-tab list/open/switch/close tools, limits a run to twelve tabs, blocks closing the source tab, groups newly created tabs when Chrome supports tab groups (using the existing `tabs` permission), and does not require a second Tabs permission. `page_open_tab` keeps one work tab per site: a requested destination already shown by an owned tab (matched on origin + path, ignoring query/fragment) is adopted in place — `reused: true` with the normal ready/tabError contract — and any other same-origin open navigates the run's existing non-source tab to the new URL (`navigated: true`, source tab never hijacked, unavailable tabs skipped) instead of creating a duplicate tab; `page_open_link` navigates the current target tab in place by default; `background: true` delegates to the owned-tab opener for explicit multi-page research. The Act prompt states that ordinary work stays in the current tab, directs the model to call `page_list_tabs` before opening a separate tab, reuse the site's work tab, and never re-perform a step whose receipt, note history, or planner state already shows success. An unrequested model-entered cross-origin `page_open_tab` destination requires user confirmation; user-named destinations and links observed in the page do not. Opened and switched tabs pass a bounded document/bridge readiness check; background tabs do not retarget the run. A bridge failure quarantines only the affected tab and allows the run to continue on another healthy tab; after a user reload, a fresh `page_get_state` can re-probe the failed source tab. Run teardown clears the page-action session in every owned tab before disposing the lease.
- `page_request_user_input` is a bounded clarification tool. It is available only in an Act-enabled run, blocks secret/payment questions, and waits for an extension-page response with a timeout or abort path. `page_pause_for_user` is a separate safe manual-intervention checkpoint that requires explicit Resume and fresh inspection.
- Act owns initial observation before any provider-directed action. Non-Hermes requests receive the synthetic inspection pair; when recovery has cleared the snapshot, only `page_get_state` is advertised with automatic selection. A forced custom tool resumes only after inspection. The Act prompt names the callable tools and directs execution of achievable page tasks.
- The page-actions system-prompt block is directive and non-limiting: the model must execute page-achievable requests with the page tools (inspect → act → re-inspect → summarize what it did) rather than describing steps. The block deliberately never enumerates capabilities the tools lack (terminal/OS actions, JavaScript, unsupported navigation), because that enumeration drove models to lead with “I can’t” refusals; `page_find_text` provides bounded read-only search for exact filters, labels, prices, and interstitial messages before scrolling; `page_wait` handles bounded asynchronous text/URL conditions instead of fixed delays, and `page_batch` combines 2–4 read-only observations in one turn; requests the tools cannot execute are answered normally as a helpful assistant, and the model never fakes an action. A provider response may bundle several tool calls, but only one state-changing page action from that batch is dispatched: later mutations receive `PAGE_ACTION_REFRESH_REQUIRED` and must use the refreshed snapshot from the first result. Approved navigation-capable controls may transition the current tab once; unexpected active-tab changes discard the old snapshot and require `page_get_state` before continuing the same request. The model must follow that recovery notice instead of claiming that page tools are unavailable. Compact results include a bounded safe link list with an `opensNewTab` hint; use `page_open_link` for `_blank` links without probing with a blocked click. Validated HTTP(S) links may navigate under the bounded Act lease; `page_open_link` navigates the current target by default, while `background: true` opens a separate owned tab for explicit multi-page work. A model-entered cross-origin destination not named by the user or observed as a page link requires an explicit confirmation; ordinary observed-link navigation remains covered by the bounded Act lease. Secrets stay out of the page tools. Empty snapshots tell the model to ask the user to open the target page.
- Frame outlines are merged by the background from per-frame content-script snapshots. `frameOrigin` is normalized to a public HTTP(S) origin and stays out of model results; the background keeps the bounded global-index-to-frame route map for the current snapshot. Mutations use the frame-local snapshot ID and element key. `RunOrchestrator` evaluates low-risk site trust and confirmation against the target frame origin. Never route an unmapped frame index to the top document.
- Site policies are background-owned and snapshotted at run start. Each action checks the current owned target origin; known navigation destinations and landed/redirect origins also pass the gate before extraction. A blocked site clears the snapshot, withholds further tools and returns `PAGE_ACTION_SITE_BLOCKED`. Approval-card site trust saves only the displayed live frame origin after confirming the top-level document origin is unchanged. Sensitive password-manager vault, identity/account, and Prompt Paul origins ignore saved low-risk and run-wide approval. Blocks and removal of a low-risk allowance tighten active runs at the next action boundary; new allowances apply to new runs. Requested tab IDs pass controller ownership checks before their metadata is read. Every awaited policy boundary rechecks run lifetime so Stop cannot create a late approval or action.
- Evaluation dry runs report intended risk and confirmation requirements without dispatch or user approval; hard blocks still apply. Actual high-risk actions always confirm.
- Page-action policy is snapshotted at run start. Default mode confirms state-changing actions; trusted mode only skips allowed low/medium-risk approvals. “Approve similar actions this run” skips allowed low/medium-risk confirmations for this run only. High-risk actions always confirm, including indexed links. Planning never enables automatic approval. Hard blocks stay unchanged. While a confirmation card is pending, the run budget clock pauses: `approvalWaitStartedAt` is recorded on emission and the run deadline is extended by the elapsed wait (capped at 10 minutes) when the decision resolves, so an open card never burns budget and an abandoned card cannot immortalize the run. Denials and timeouts record a bounded `lastDeniedAction` (name + timestamp only) that surfaces as a distinct declined outcome on the progress card and a “change approach, do not repeat” nudge in the next system prompt; the marker clears on the next approved decision or fresh inspection.
- Act-mode instructions require the model to continue multi-item or ongoing page workflows after partial progress instead of returning an interim next-step menu; it may ask only when real ambiguity, a blocked action, or a safe manual step prevents progress.
- Brave execution is supplied through `braveSearchExecutor` and key availability through `webSearchStatusProvider`; `run.config.apiKey` is only the selected LLM credential.
- Search/tool sequencing is model-directed before use: a forced user tool (when configured) runs first exactly once, then `web_search` is offered with automatic model selection (never forced) while a search slot is available. The slot is claimed before network I/O.
- After a search attempt, the system prompt switches to an already-completed phase and the immediate continuation is text-only. Duplicate or parallel search calls receive `WEB_SEARCH_ALREADY_USED` and never issue another Brave request.
- A search response with no usable normalized sources produces `WEB_SEARCH_NO_RESULTS`; it is not treated as successful grounding.

## Local Contracts

- Navigation links are supported only when the snapshot exposes a validated HTTP(S) destination. Same-tab links use `page_click`; links that open a new tab use the indexed `page_open_link` tool. Observed cross-origin links are covered by the Act lease; an unrequested model-entered cross-origin `page_open_tab` URL requires confirmation, while writes and risky controls still require approval. An active target tab that changes documents independently is adopted automatically and inspected before any mutation.
- Act page snapshots are DOM-only: they do not capture or attach screenshots, draw index overlays, or send `visualBoxes`. Keep the independent video/content-extraction screenshot path unchanged.

- Skills are injected as instructions via the composed system prompt (`_buildSystemPrompt`), not via conversation history unshift. Requested skills are resolved through `resolveSkill` and included even when `disable-model-invocation` hides them from model self-discovery.
- Tool executions must remain idempotent by `runId` and `toolCallId`. Before every state-changing page or owned-tab action, the orchestrator persists a bounded session checkpoint. Failed or interrupted dispatch leaves an in-flight checkpoint for explicit recovery; normal completion and terminal cleanup remove it. Mutation uncertainty is never resolved by blind replay.
- The tool-call retry cap counts consecutive failing tool turns only: a successful tool result resets the counter, and Act denials/timeouts or actions proven not delivered do not count as tool failures. When repeated Act failures reach the cap, the run asks for a toolless final answer instead of surfacing the raw retry error. Multi-step page automation (inspect → act → re-inspect) can run up to separate observation/navigation/mutation budgets (256/96/64). Bridge readiness and navigation polling use bounded exponential backoff with jitter. Mutation results carry a refreshed-snapshot notice and a bounded selector-free `scopeDiff`, so the model re-reads the current `snapshotId` and indexes instead of reusing stale ones. State-changing page actions return bounded delivery receipts with action-specific evidence; `not_delivered` means no page change occurred and the final response must say the action was not performed. Unchanged `delivered_unverified` mutations are not retried. The same-mutation loop guard records only executor-delivered mutations, so stale or obscured dispatch failures cannot lock out the required action; three delivered repeats without visible change still block. A separate target-keyed toggle guard detects A→B→A or 3 mutations in 6 actions, warns on detection, and blocks the next repeated target until another target is activated; fresh inspection alone does not clear it. An identical-query guard normalizes `page_find_text` queries and submitted `page_input` text (case/whitespace-insensitive, ≤160 chars) and blocks the third identical attempt without verified progress, directing the model to open an observed match or refine the query; verified non-search navigation clears it, while navigating search submissions and verified field read-backs do not. A separate unopened-search counter blocks further find-text and submitted-input searches after six consecutive searches with no verified result opening, directing the model to open the best observed match; verified `page_open_link`, `page_open_tab`, and non-search navigations clear it. `page_record_note` stores up to 72 short untrusted observations, optionally records a bounded `item` with `done`/`skipped` status for a counted quota, and rejects secret/credential/payment wording. Old page snapshots are compacted before provider calls (history cap 360K chars).
- Checklist updates are atomic and bounded. Resolved steps remain visible; a receipt/snapshot cannot be consumed by two updates. New descriptions use the note safety gate because they can enter checkpoint metadata. The prompt shows current statuses, counted progress and remaining budget. Unresolved explicit checklists use bounded continuation turns. When all steps resolve, one fresh verified inspection precedes the text-only summary. Simple observed tasks do not get an invented incomplete-plan warning.
- Abort handling should emit a clean aborted event rather than surfacing intentional cancellation as an error.
- Provider-specific execution must preserve OpenAI-compatible and Anthropic-compatible endpoint behavior. Non-Hermes provider loops count API calls separately from tool calls, allow one toolless wrap-up call after a 500-call or 30-minute default limit, retry only bounded transient failures, compact oversized histories, and never repeat a delivered provider response after an output-safety failure.
- Hermes provider execution must use the stored Hermes profile endpoint, never accept a credential from a chat message, and may use Act/page actions only after the gateway advertises `run_client_tools` plus the documented `/v1/runs/{run_id}/tool-result` route. Client calls must pass through the existing bounded page-action policy, approvals, ownership, and receipts; unsupported gateways reject Hermes Act runs. Hermes runs send the trailing unsent local user messages as current-turn input plus a bounded explicit `conversation_history`; loaded page context stays attached while it is active and historical binary media is removed. Hermes session pointers are bound to the local conversation identity. Hermes session boundaries use `PATCH /api/sessions/{id}` with a fixed `new_conversation` end reason; only the documented `session_not_found` response may clear an already-missing pointer. Stale-run recovery must not treat unrelated 404 responses as missing sessions. One Hermes run or stopping run is admitted per profile; different profiles may run independently. Hermes Stop keeps the active run and profile guard until a remote terminal state, and control-plane requests use bounded timeouts. Hermes capability checks require the advertised run submission, status, SSE, stop, and approval features before the connection is reported as supported; released gateways (0.20.x) advertise the approval feature as `run_approval_response`, which the check accepts alongside the documented `run_approval` name. Hermes approval decisions must match the pending opaque approval ID.
- Codex subscription runs use the background-provided access token and account identifier only at request time; never persist or emit those values through run state, journals, or UI events. The selected profile reasoning level is sent as the Codex Responses `reasoning.effort` field.
- Terminal `complete` events may include safe provider completion metadata. Reasoning-only responses receive at most one text-only recovery attempt without repeating tools or exposing hidden reasoning.
- `CORE_INSTRUCTIONS` applies to all runs unless the project deliberately changes the formatting policy.

## Work Guidance

- Keep orchestration logic centralized here instead of duplicating run or tool execution flow in `background.js`.
- Hermes server tools remain gateway-owned; do not register Prompt Paul custom-tool handlers for Hermes runs.
- Register new built-in tools through the existing tool registry pattern.
- Keep skill policy aligned with root AGENTS.md and `src/utils/skillParser.js`.
- Preserve event shapes consumed by `chat.js`; page-action confirmation events must include only bounded summaries, risk, target labels, and opaque confirmation IDs, never raw DOM values or secrets.
- Runtime events carry a monotonic per-run sequence and a bounded session journal. Consecutive live `content`/`reasoning` deltas are delivered as ordered `stream_batch` segments at a bounded cadence; the chat expands them before rendering. Stream batches are live-only and do not trigger session-journal writes. The journal stores safe activity summaries only; raw DOM snapshots, tool arguments, credentials, and streaming deltas are not persisted. Development diagnostics use a separate bounded session store and must redact credential-shaped data; detailed response payloads can be console-only when they would exceed the normal journal contract.
- The background `executeRun` message is an acknowledgement boundary, not a completion stream. The worker starts `RunOrchestrator.execute()` without holding the sender's message channel open; terminal events and the bounded journal are authoritative for completion or failure.
- `ServiceWorkerKeepAlive.js` resets the worker idle timer every 20 seconds only while an execution promise is pending. `execute()` owns this lifetime; nested provider/tool turns share it, concurrent runs release it independently, and all settling paths clear the interval. Existing run budgets and decision timeouts remain in force. Idle workers and runs created without execution do not receive heartbeats.
- Development tracing is separate from the normal event stream. `RunOrchestrator` records detailed local run, provider, tool, page-action, policy, receipt, budget, planner, and recovery diagnostics only when the development build's session tracer is enabled; production builds replace the tracer with a no-op. The eval-build-only trace records the system message and up to five recent provider messages with secret redaction and size caps; it never enters normal journals or production events.

- Snapshot outlines and safe values stay in live task/history memory. Events and journals receive only bounded metadata and receipts. Register page_set_value as a mutation; indexed read-only scrolling must validate snapshot/key identity just like hover. Removed node IDs fail closed instead of semantic rebinding.
- In evaluation dry-run mode, the first intercepted mutation is authoritative: expose one final page inspection, then no more tools; reject direct follow-up calls and tell the model the requested change was not performed.
