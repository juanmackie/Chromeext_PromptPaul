## Observed product and implementation

OpenUI is a generative UI framework, not a ready-made browser assistant. Its central format, OpenUI Lang, is a compact line-oriented program describing a tree of components from an application-defined library. The application derives model instructions from the library, streams the model output, and renders the parsed program into components it owns. OpenUI documents forms, tables, charts, cards, domain-specific controls, and progressive rendering in a chat. The component library determines what can be generated and how components behave. [OpenUI overview](https://www.openui.com/docs/openui-lang/overview), [Generative UI](https://www.openui.com/docs/agent/core-concepts/generative-ui)

The official renderer docs describe streaming parsing, schema/component validation, form-state callbacks, action events, and optional tool providers. `Query` and `Mutation` statements call application-supplied functions or an MCP client; generated interfaces can refresh queries or submit mutations locally without another model call. `@ToAssistant` can instead return an interaction to the conversation. Thus useful live data or write actions require the host application to deliberately expose those tools. [Renderer](https://www.openui.com/docs/openui-lang/renderer), [Interactivity](https://www.openui.com/docs/openui-lang/interactivity), [Queries and Mutations](https://www.openui.com/docs/openui-lang/queries-mutations)

The repo describes an open-source SDK with a framework-agnostic language core and first-party framework adapters; the renderer documented for the main integration is React. A browser bundle is also listed. The repository `LICENSE` is MIT. OpenUI Cloud/Gateway is a separate managed product: it provides a unified API, output correction/validation while streaming, and provider failover. Its docs require generation API credentials to stay server-side; browser access uses short-lived scoped frontend tokens. [OpenUI SDK reference](https://www.openui.com/docs/api-reference), [Pinned README](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/README.md), [MIT license](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/LICENSE), [Gateway overview](https://www.openui.com/docs/gateway), [Gateway authentication](https://www.openui.com/docs/gateway/authentication)

OpenUI’s homepage says the generated UI is restricted to application components and does not run arbitrary code. Its claims of “3x faster” rendering and up to 67% fewer tokens are marketing/benchmark claims, not independently validated here; the homepage also reports a different benchmark comparison in its FAQ. Treat those numbers as unverified for PromptPaul workloads. [OpenUI homepage](https://www.openui.com/)

OpenUI Cloud pricing is distinct from the MIT SDK. The pricing page currently lists a free Gateway tier with 3,000 calls/month and paid tiers, with model tokens charged separately; it also says free models may use data for training. Pricing and terms can change. The open-source SDK can call a model directly and does not require Gateway. [Pricing](https://www.openui.com/pricing), [OpenUI overview](https://www.openui.com/docs/openui-lang/overview)

`createParser(schema)` and `createStreamingParser(schema)` expose typed parse results/element trees. The evaluator interprets a custom AST; the inspected parser/runtime paths did not expose `eval` or `new Function`. That finding is narrower than a complete security audit. No explicit input-byte, nesting-depth, statement-count or evaluation-budget limits were found in the inspected parser paths. Post-parse shape validation alone would not bound work done while parsing hostile input. Any adoption needs pre-parse limits and a proven depth/work boundary, or should fall back to the native contract. [Parser API](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/packages/lang-core/src/parser/parser.ts#L638), [AST evaluator](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/packages/lang-core/src/runtime/evaluator.ts#L40).

The runtime intentionally dispatches model-selected tool names and arguments through an application-supplied provider. `Query` can execute on load/render; `Mutation` executes through actions. Duplicate-submit protection is not an authorization policy. The proposed passive adapter must reject `Query`, `Mutation`, `Action`, `Run`, and other active constructs before evaluation, omit the tool provider, and avoid the reactive runtime. Component schemas alone do not enforce Prompt Paul's permission rules. [Query dispatch](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/packages/lang-core/src/runtime/queryManager.ts#L208), [Mutation dispatch](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/packages/lang-core/src/runtime/queryManager.ts#L471), [Language specification v0.5](https://www.openui.com/docs/openui-lang/specification-v05).

The language specification version is separate from package semver. The browser bundle README also appears to lag its package/API: its example names `code`/`schema`, while current renderer source/docs use `response`, `library` and `isStreaming`. Pin and test the actual installed exports rather than copying a README example. [Renderer source](https://github.com/thesysdev/openui/blob/c4c0c90575facf824d3d8a64daa11947acc8a668/packages/react-lang/src/Renderer.tsx#L15), [Renderer documentation](https://www.openui.com/docs/openui-lang/renderer).

## Fit for PromptPaul

PromptPaul is currently a Manifest V3 extension with a plain JavaScript/HTML side panel and provider adapters for API-compatible endpoints, Codex, and Hermes. Its existing chat flow already streams responses, composes bounded page/selection context, and supports explicit tool/action policy. The package manifest does not include React or OpenUI. [PromptPaul architecture](ARCHITECTURE.md), [PromptPaul README](../README.md), [package.json](../package.json)

The most fitting product opportunity is optional structured answer rendering in the side panel: summary/key-value cards, responsive comparisons, and local exploration controls. Ordinary Markdown tables and grounded source lists already exist. The new value is consistent narrow-panel layout and interaction rather than basic table support. Charts and generated forms are possible later extensions, with greater data-validation and state-management costs. A first version could render a small, extension-owned allowlist of read-only blocks with existing theme tokens and a text fallback. This is a proposal inferred from OpenUI's constrained component model and PromptPaul's composer-led UI.

Another useful pattern is explicit interaction semantics: a generated control can either update its own local display, submit a bounded structured follow-up to the current conversation, or invoke a separately authorized PromptPaul tool. For this extension, page actions and mutations should continue through its current consent and policy layer; an OpenUI-shaped button must not become a bypass around Act confirmations, provider tool support checks, or structured context composition. OpenUI docs establish that local updates and tool calls are distinct runtime paths; the PromptPaul boundary recommendation is an inference from its repository contract.

## Prioritized opportunities

1. **Compare a small native response contract with the independent OpenUI parser.** Use the same summary/key-value/comparison fixtures, bounded sizes, accessible layouts and ordinary text fallback. Measure total prompt/output tokens and failures, not only output compactness. Ship the smallest viable option; defer charts and forms.
2. **Add explicit follow-up controls.** Examples: switch comparison dimensions, filter rows, or ask a question about a selected row. Keep local view state distinct from conversation actions, and route conversation actions through the existing run path.
3. **Keep page data read-only in generated UI initially.** Displaying model-derived views of already attached page content has lower integration cost than exposing arbitrary `Query`/`Mutation` backends. For browser actions, retain Act’s existing approval receipts, hard blocks, and bounded budgets.
4. **Treat the full UI SDK as a separate decision.** Core-parser adoption does not require React; full renderer/chat-SDK or browser-bundle adoption does. The existing build copies local assets rather than bundling npm imports, so even core adoption needs a packaging decision. Browser-bundle compatibility with this extension's CSP/build pipeline was not tested.

## Verified local seams

- `src/chat/ChatUI.js:85` renders assistant Markdown and copy controls; `src/chat/ChatStream.js:82` reparses accumulated text after batched deltas. An answer renderer should be a small module integrated here, with stable card DOM only in a later progressive-rendering stage.
- `chat.js:2180` receives text deltas and `chat.js:2402` handles completion, final rendering and text history. API, Codex and Hermes converge on common events; a provider-neutral completion enhancement avoids three separate implementations. `RunOrchestrator.js:5737` also commits assistant text to its own provider history, so UI-only parsing would not normalize subsequent provider turns. A structured-answer implementation needs explicit wire framing and normalization at that shared boundary before history and journaling.
- `src/chat/ChatGrounding.js:150` normalizes/prints source links and `:237` preserves recovered-text truncation notices. Reuse this metadata; generated labels/URLs do not independently establish grounding.
- `src/orchestrator/RunOrchestrator.js:6017` bounds terminal journal content to 8,000 characters. Keep readable fallback text in this existing recovery path rather than persisting arbitrary structured payloads.
- `src/utils/domSanitizer.js:20` uses DOMPurify or escapes everything if unavailable. Native cards should insert untrusted data through text nodes and keep sanitized Markdown for prose.
- `manifest.json:22` enforces local extension-page scripts. `package.json` has no React runtime. `scripts/build.js:169` copies extension assets; adoption requires deliberate local packaging and licence records.

These references were inspected at the local revision above. This review did not diagnose a runtime defect or verify a live integration.

## Risks and limits

- Generated UI adds a second rendering format to chat history, editing, retry, reconnect, accessibility, and theme behavior. Preserve readable text when parsing fails or the provider emits ordinary prose.
- Treat generated props, URLs, action payloads, and page-derived values as untrusted. A constrained renderer reduces executable-code risk but does not make unsafe links, deceptive UI, or sensitive context harmless.
- Avoid remote OpenUI Cloud for a first experiment unless the product intentionally accepts its additional vendor, credential, privacy, pricing, and retention boundary. PromptPaul’s contract keeps provider credentials background-owned; Gateway keys must never be exposed to extension pages.
- `Query`/`Mutation` capabilities need an explicit tool allowlist and per-action policy. They must not directly mutate a website or bypass PromptPaul’s Act confirmation system.
- Generated charts need validated numeric inputs, labels, and empty/error states; they should not imply precision unsupported by the page or model evidence.
- No live provider generation or real-browser rendering was performed for this review. The browser automation CLI was reported unavailable in the parent task; this note is based on docs/source review only.
