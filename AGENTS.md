# Chromeext_PromptPaul agent contract

## Operating Standard

- Apply the active global AGENTS.md instructions as the repository operating standard.
- This file is the nearest-owning contract. It refines the parent policy with repository-specific facts and cannot weaken a mandatory parent rule; conflicts resolve to the parent.

## Scope and Ownership

- Root owns project-wide contracts, `manifest.json`, package metadata, root extension entry points (`background.js`, `chat.js`, `options.js`), content scripts, HTML/CSS entries, theme/loading helpers, `ui-primitives.css`, README/changelog files, and the durable `REVIEW_PLAN.md` review record. Transient `PLAN.md`/`plans/` drafts stay untracked.
- Child docs own the durable subtrees listed under Child contracts below. Read the applicable child contract before editing inside its scope.
- Put new business-capability logic under an owning `src/<capability>/<use-case>/` area. Keep `src/utils/` for stable behavior genuinely shared across capabilities; root entry points compose modules instead of owning growing implementations.
- `dist/`, `dist-dev/`, and `dist-eval/` are generated build output, not source of truth; never edit them directly. `dist-dev/` and `dist-eval/` are local-only development output and must never be packaged or published.
- Do not edit vendored libraries or binary assets unless the task is specifically about them.

## Constraints

- Manifest V3 extension; `background.js` is an ES module service worker; extension-page CSP is `script-src 'self'`. Use 2-space indentation, single quotes, and `@fileoverview`/`@module` JSDoc in new modules under `src/`.
- API keys, profiles, instructions, tools, skills, and settings live in Chrome storage. Codex subscription and Hermes gateway credentials are background-owned and keyed by profile; they never appear in profile records, run configs, events, logs, backups, or chat/UI messages, and are never exposed to the Options page.
- The storage schema is stable: canonical keys (profiles, `lastSelectedProfileId`, instructions, customSkills, promptPaulTools, analytics keys, voice-input keys, `braveSearchApiKey`, `exaSearchApiKey`, web-search/page-action/notch/theme keys, `hermesApiKeys`/`hermesSessions`/`hermesSessionKeys`, `promptPaulActCheckpointsV1`, `pageActionSitePolicies`, `pageActionsPreciseInput`) are pinned by regression guards. `pageActionsEnabled` is session-scoped and excluded from backups; backups export only supported persistent settings and restore profiles without credentials.
- Remote LLM calls happen only when the user sends a prompt or invokes an action. User-supplied media URLs are restricted to bounded public HTTP(S) fetches with private-host, media-type, redirect, timeout, and response-size guards. Browser-internal pages, extension pages, and Chrome Web Store pages are blocked or reported before content extraction. Broad host permissions are intentional for extraction and context-menu workflows.
- Runs: `makeApiCall`/`makeApiCallWithMedia` require `beginResponseRun()` before any side effect and `endResponseRun()` in `finally`. Live `content`/`reasoning` deltas may arrive in ordered `stream_batch` events at a bounded cadence; the chat expands their segments before rendering, and stream batches are not persisted. Act bridge readiness may be cached for up to 60 seconds per tab/document, with invalidation on navigation, tab removal, teardown, or bridge failure; readiness is never marked while the tab is loading, and only a definite no-receiver failure may trigger one safe re-injection and retry (a closed response port is not retried); run startup still verifies readiness. A missing child-frame bridge is revalidated against its current origin and site policy before targeted injection and one read-only retry. The `executeRun` bridge acknowledges immediately; terminal status arrives via ordered `orchestratorEvent` messages and the session journal, with an opaque owner token kept by the owning chat (reconnect may adopt it, never persisting it). Non-Hermes runs use bounded API-call/wall-clock budgets, one toolless wrap-up, bounded transient retries, context compaction, reasoning-aware timeouts, and repetitive-output protection. The wall-clock deadline is paused while an Act confirmation card waits for a user decision: the elapsed wait is bounded and the deadline is extended by up to 10 minutes on resolution so an open card does not burn budget.
- Executing runs reset the service worker idle timer through a run-scoped extension API heartbeat. Nested turns share that heartbeat; completion, error, and Stop release it. Idle workers and unexecuted runs receive no heartbeat. Browser lifecycle tests must leave the worker debugger detached so normal shutdown remains observable.
- Privileged background messages require an extension-page sender; content-script requests are bound to the sender tab; provider credentials resolve from the saved profile in the background.
- Providers are `api`, `codex`, or `hermes`. Hermes profiles use gateway sessions, bounded `conversation_history`, server-side tools, and approval events; runs, resets, and session-key operations serialize per profile; Act requires the gateway to advertise `run_client_tools` plus the tool-result endpoint (otherwise Act runs fail with an actionable message); Stop holds `stopping` until the gateway reports terminal; idle action is **New chat** (ends gateway session, clears pointer, keeps local conversation identity). Codex: device-code login creates/selects the `Codex` profile; discovery includes the required extension client version; restored Codex profiles require sign-in again. Codex auth stays in `src/utils/codexAuth.js`, model discovery in `src/utils/modelDiscovery.js`, wire conversion in `src/orchestrator/CodexTransport.js`.
- All entry points (context menus, deep links, toolbar action, website deep links via `externally_connectable` for promptpaul.juanmackie.com) funnel through the side panel via `sendPanelMessage`/`openChatWithContext`. The Options page calls `chrome.sidePanel.open()` from its button gesture. `chat.js` resolves run source tabs via `getRunSourceTabId()`; sticky selection release is provenance-aware (`selectionOwnsTabId`); pending panel actions are consumed locally, not re-sent.
- Chat is composer-led: all send/action flows route through `#input-area`, with composer UI logic in `src/chat/ChatComposer.js` (context tray, quick-action row capped at four visible actions, inline Stop/Retry/Edit/Continue). Suggestions consolidate into one row; starters reuse the canonical current-page load path. Page-scoped quick actions (site action cards, Summary/TL;DR/Technical) carry the attached page as `page_content` context in their own request instead of relying on an earlier history turn.
- Context-bearing prompts use structured prompt request objects and `composeUserPrompt` — never raw concatenation of selection, page content, media, or metadata. Untrusted context stays bounded and marked as source material.
- Answer cards are an explicit, run-local `answerFormat: 'cards'` mode. `src/utils/answerSchema.js` bounds and validates passive summary/key-value/comparison data; `ChatAnswerRenderer.js` renders a fresh allowlisted projection. Complete validated blocks may appear progressively with host-issued turn/index identity; terminal validation is authoritative, and invalid/interrupted output removes previews. Local comparison controls preserve existing nodes, focus, and reader scroll. Card follow-ups prefill the composer with bounded original context/source provenance and start no run until Send. Readable answer text remains authoritative for history, copy, and the existing bounded journal. Card data and local interaction state are live-only; they grant no tool, page-action, or network authority.
- Page actions (Act) are default-off, DOM/semantic-only, session-scoped. The semantic runtime lives in `content_script_page_actions.js` and is injected on demand; `content_script_unified.js` remains the always-on extraction bridge. Every non-Hermes Act run executes an initial `page_get_state` before the first provider request and serializes a matching synthetic tool pair; Hermes retains gateway-directed inspection; password/OTP/payment/credential/security/destructive controls are masked, confirmation-gated, or blocked; trusted mode never enables JavaScript; opt-in precise input is limited to `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, and `Input.insertText` in `CdpInputBackend.js`, while page JavaScript, screenshots, network and DOM CDP methods remain outside the contract. Budgets: 256 observation / 96 navigation / 64 mutation actions; model-maintained checklist ≤12 steps, ≤5 revisions, counted quota ≤12; planning never changes consent, and high-risk actions always confirm even after “Approve similar actions this run”; automatic Act working memory holds 16 action-ledger entries and 72 opaque visited target/route keys per run; persistent origin policies (`allow_low_risk` or `block`, ≤200) are snapshotted at run start; new blocks and removals of low-risk allowances tighten active runs at the next action boundary, while new allowances apply to new runs; sensitive password-manager, sign-in/account, and Prompt Paul origins never accept or honor low-risk/site or run-wide similar-action trust; blocks stop Act before inspection, including redirect/recovery dispatch; site trust never skips high-risk confirmation; task memory 72 notes, 360K history chars; up to 12 run-created tabs with one work tab per site; Chrome groups run-created tabs when the browser supports tab groups; mutations return `not_delivered`/`delivered_unverified`/`delivered_verified` receipts, and unverified mutations are not retried blind. A target-keyed toggle guard warns on A→B→A or 3 mutations in 6 actions and blocks the next repeat until another target is activated. Route evidence is digest-only; action memory is neither checkpointed nor journaled. Page-action tools accept an optional bounded model-supplied step `title` (≤80 chars, no control characters or credential/payment wording) validated by the policy layer for progress-card display only; a denied or timed-out decision records a bounded last-denied marker that drives a distinct declined card outcome and a “do not repeat it” planner nudge. Session checkpoints never store DOM, page text, notes, or credentials; resume always clears stale state and forces fresh inspection.
- Act checklists use `page_update_plan`; completion needs new observed evidence. Terminal progress and completion carry bounded `actOutcome {status, reason}`, derived from runtime state. Denials, timeouts, skipped work, loops, budgets and site blocks cannot report success. Model discovery records advertised tools support; enabling Act warns for unsupported or unknown API models without a provider request.
- The Top Notch is Shadow-DOM isolated, edge-pinnable (`notchPlacement`/`notchPosition`), theme-following, holds no credentials, and dictation uses a short-lived background-owned lease so `sidePanel.open()` stays inside a user gesture. Notch-routed IDs and text are validated by the background worker.
- Act settlement retains the 100 ms DOM-quiet path and a 1 s overall deadline, including animation frames, extending to at most 3 s only for newly action-triggered busy controls or resource entries inside the quiet window. Existing spinners do not extend the wait. Results include bounded settlement timing and reason. Hidden tabs finish through timers; visibility changes during the frame wait must not strand an action or quarantine a healthy bridge. Settlement releases its DOM/resource observers, timers, frame callbacks, and visibility listener.
- Dropped `.txt`/`.md`/`.markdown`/`.csv`/`.json` files attach as bounded text via `ChatMedia.prepareDroppedFile()` (memory only, one at a time) and never enter the base64/vision pipeline; other drops keep the media flow. PDF extraction parses bytes through the bundled pdf.js path, not Chrome's viewer DOM. Site extraction adapters live in `src/utils/siteExtractors.js` and must stay aligned with the classic content script mirror.
- Run/feedback states use the `data-run-state` vocabulary (`idle`, `running`, `streaming`, `stopping`, `complete`, `error`, `stopped`) driven by `src/utils/runState.js`; `ui-primitives.css` depends on `theme.css` tokens and loads after it on every extension page.
- Web search grounding: Exa (keyless, hosted MCP, with an optional background-owned `exaSearchApiKey` that only lifts Exa free-tier rate limits; never exposed to the Options page as a value and excluded from backups) falling back to Parallel's keyless hosted Search MCP, or Brave (keyed, key background-owned, never reused from LLM profiles), selected by `searchProvider` (`exa` default, `brave` keyed; a stored legacy `duckduckgo` migrates to `exa`); `web_search` is a reserved tool name enforced in `src/chat/ChatAPI.js`, `src/orchestrator/RunOrchestrator.js`, and `options.js`; search is model-directed permission, not a mandate; one search slot per run; empty results are `WEB_SEARCH_NO_RESULTS`, not a grounded response.
- Skills follow the Agent Skills spec (`SKILL.md` with YAML frontmatter; `name`/`description` required; `command-dispatch: tool` for deterministic execution) with built-ins registered in `skills/skills.json` (`humanizer`, `weather-guide`). Skills are instructions by default, not executable tools, unless deterministic tool dispatch is explicitly implemented. `docs/SKILL_EXAMPLES.md` holds user examples.
- Analytics stay opt-in with safe-label handling and a rotating pseudonymous instance ID. Fresh checkouts seed the Default profile with OpenRouter's OpenAI-compatible endpoint and `openrouter/free` model but no credential; existing profiles are preserved.

- Act observations use a viewport-anchored outline (24K characters), at most 200 controls per snapshot, and document/session-stable node IDs. The on-demand Act runtime also inspects up to 16 frames per tab, merges labelled frame sections, routes indexed actions to the owning frame, applies blocked-origin policies per frame, and omits payment-like or blocked frames. The background merge remaps each frame's outline markers and top-frame region indices to the single merged positional numbering, so the numbered control the model reads is the control a dispatched index reaches. It uses the scripting API's frame IDs without `webNavigation`; missing child bridges are revalidated per frame and injected only into the current `documentId`, and frame responses must match the validated origin; per-frame sensitive-value masking remains active. Open shadow roots are included; removed nodes require fresh inspection. Non-sensitive field values are bounded to 160 characters each and 8K total; focused-target and submit-control metadata are value-free. Sensitive values stay masked and values never enter journals or checkpoints. Invalid state (`aria-invalid` or failed native validity) and bounded field-error text from `aria-errormessage`/`aria-describedby` are disclosed for non-sensitive controls only; sensitive controls keep the invalid flag without error text. Bounded form notices (`role=alert`/`status`/`log`, `aria-live`) are collected at most 8 per snapshot, 200 characters each, reserve room inside the outline cap, and participate in change detection while raw values never enter journals or checkpoints. Scalar value-setting, append input, indexed/focused/modal scrolling and optional declared postconditions use existing policy, budgets and receipts.

## Verification

- `npm run test` — module structure, manifest references, skill files, regression guards (`scripts/test-runner.js`).
- `npm run test:behavior` — vitest behavior suite (`vitest.config.js`).
- `npm run test:browser` — Playwright real-browser coverage (`playwright.config.cjs`, `tests/browser/`).
- `npm run smoke` — manifest file references and vendored dependency conflicts (`scripts/smoke-check.js`).
- `npm run validate` — lint, format check, tests, behavior suite, smoke, vendored-license verification (see `package.json` scripts; all component scripts exist there).
- `npm run build` / `build:dev` / `build:eval` / `build:prod` — generate `dist/` variants (`scripts/build.js`).
- For UI or browser-runtime changes, also reload the unpacked extension in Chrome or Edge and exercise the affected flow by hand; a passing build is not evidence of visual or interaction correctness.
